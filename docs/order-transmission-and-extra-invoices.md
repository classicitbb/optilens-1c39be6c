# Order transmission and additional invoices

New Rx submissions default to Gatekeeper. The shared **Auto-transmit to Gatekeeper** switch on Rx & Stock Orders is a persistent administrator setting. It applies to new submissions; enabling it never releases the existing backlog. Switch it off for manual-release testing. Fixture/test-bench Rx quotes remain excluded from the outbox. Stock **Save draft** is always a draft; **Submit stock order** releases through the selected sender only when auto-transmit is on, otherwise it stages for staff release. OptiLens remains an explicit manual alternative.

The database wakes Gatekeeper after commit, with a once-per-minute recovery schedule for a missed wakeup. Only approved Gatekeeper rows marked for automatic delivery are eligible. Each request claims an order atomically. Failed, claimed or accepted orders are not replayed automatically. Automatic delivery does not fall back to OptiLens. Problems remain visible in the workspace and dispatch logs; only a retained Gatekeeper receipt proves acceptance. Customer release emails retain their separate, off-by-default toggle.

Published products can be ordered without an account price. Assigned pricelist prices are used when present; another customer's Retail price or a generic catalogue price is never substituted. Staff-only services retain their explicit service price. An unquoted stock line carries `price_pending` and a lab instruction to confirm the price and hold shipment. Zero in the stored known-price subtotal does not mean the item is free. Product, active-variant, quantity and lab SKU checks remain enforced.

In an order's **Summary**, editing staff can issue an itemised additional invoice for unquoted items, requested extras or notes. The invoice is in BBD, including applicable tax as entered by staff. Website orders bill their original owner. For an internal stock/Rx submission without a website order, staff must choose an approved portal user linked to that customer account. The same request key prevents duplicate invoices when the client retries.

The customer's cart lists their unpaid additional invoices separately from products. **Review & pay invoice** opens the existing customer-device payment review, then the existing hosted card checkout. Prices and totals come from the server invoice. Payment tokens are hashed, short-lived and single-use. Paid invoices disappear from the outstanding list only after trusted payment settlement. A started or failed payment requires staff review before another attempt, avoiding an ambiguous duplicate charge.

The application refuses website order status changes to shipped/delivered/completed while an extra invoice is unpaid, or an unquoted submission has no settled supplementary invoice. Once all invoices settle, that database hold clears automatically. External Gatekeeper/Innovations physical dispatch is controlled by the lab: stock files carry the hold instruction, and staff must honour it there. This website cannot remotely stop a parcel already dispatched in another system. Internal submissions without a website `order_id` expose the invoice/hold in the workspace but have no website shipping-status row to block.

Implementation: `order_dispatch_settings` is server-only; only the admin setter changes the switch. Its endpoint and public gateway key are derived from the existing scheduler configuration, with a dedicated dispatch token. `order_extra_invoices` has RLS, owner/staff reads and no authenticated direct writes. Scoped RPCs issue invoices, list permitted invoices, and mint owner-only payment links. Existing walk-in payment settlement remains authoritative; no new payment-provider integration or secret is introduced.

Validation: unpriced-item regression reproduced against the hosted pricing function, then verified pending instead of rejected. Both migrations and synthetic invoice issuance, idempotency, owner access, amount matching, unpaid shipping block and simulated settlement were rehearsed in one rolled-back transaction. No fixture order, invoice, payment or network send committed. New unit/integration tests cover invoice presentation, payment refusal, automatic batch bounds/token scope and stock manual mode. Live function bodies and privileges were checked after the user applied the migrations. No real order transmission or card charge is part of verification.
